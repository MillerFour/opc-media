# 公众号创作系统 · 规划（v1）

> 2026.11.07 ｜ 目标：把现在这套「人肉作坊」变成可复用的两条流水线——**系列创作**与**随笔创作**。
> 本文只解决"怎么组织"，不规定"怎么写"（写作规范见 `.workbuddy/style-guide.md`）。

---

## 一、先诊断：现在的瓶颈不在写作

已经能跑的部分：4 套风格模板、参数化封面生成器、言序推送链路、git 自动提交、25 篇文章的实战经验。

真正的断点有四个：

| 断点 | 现象 | 后果 |
|---|---|---|
| **没有状态** | 每篇做到哪一步（大纲/正文/封面/推送/已审）只存在对话里 | 换会话就丢，重复劳动，不知道自己手上还有什么没发 |
| **选题靠临时起意** | 看到热点就写，写完才发现和系列撞车 | 系列断更、选题重复、时效过了才动手 |
| **规范靠全量注入** | 每次写作先读 168 行 style-guide | 上下文被吃掉，风格细节反而容易漏 |
| **推送靠记忆** | theme_id、account_id、图片张数限制、异步规则全在脑子里 | 每次重填，出错重来 |

**结论：这个系统的第一性需求是"状态机 + 台账"，写作能力本身已经够了。**

## 二、系统分层（四层，从下往上建）

```
L3 交互层   /series  /essay  /status        ← 你只跟这三个打交道
L2 流水线   选题 → 定位 → 大纲 → 正文 → 素材 → 审查 → 发布归档
L1 数据层   topics.yaml · series.yaml · 每篇 manifest.yaml
L0 资产层   风格卡 · 正文模板 · 封面生成器 · 插图模板 · 口径库
```

建的时候**从 L1 往上**，不要从界面往下。没有台账的自动化，只是把混乱加速。

## 三、模块一：文章风格模板（资产化，不是文档化）

现在的问题是：模板是 HTML 文件，规范是 md 文件，两者靠 agent 每次现读现理解。改成**三件套**：

| 组件 | 位置 | 作用 |
|---|---|---|
| **风格卡** | `00-系统/styles/锌白.md` 等 4 张 | 每张 ≤300 字：配色 hex、结构骨架、写作纪律 3 条、禁忌 3 条、选型直觉一句。写作时**只读对应的一张卡** |
| **正文基线** | `00-模板/style-*.html` | 结构参照，照抄骨架换内容 |
| **封面生成器** | `00-模板/cover-generator.py`、`00-系列_*/gen_cover.py` | 参数化出 2.35:1 + 1:1，禁止手改截图 |

风格卡的字段固定，方便以后机读：

```yaml
style_id: zinc
name: 锌白
aliases: [周报, 终端风]
palette: {bg: "#ffffff", ink: "#09090b", sub: "#52525b", line: "#e4e4e7", wash: "#fafafa"}
skeleton: [头部黑卡, 章节标题, 要点卡 ×N, 数据卡, 附录卡, 口径卡]
rules: ["所有 section 显式 text-align:left", "强调只用加粗不染色", "数据用等宽字体"]
forbidden: ["彩色高亮", "渐变", "AI 生图做封面"]
best_for: 科技/数据/清单/人物档案
cover_theme_id: terminal
```

`cover_theme_id` 是关键：**风格卡直接告诉推送脚本该用哪个主题**，不再靠记忆。

## 四、模块二：选题管理（一个池子，两种来源）

### 4.1 选题池 `00-系统/data/topics.yaml`

```yaml
- id: wtg-05
  title: 工程师的六年
  type: series            # series | essay
  series_id: wittgenstein
  volume: 5
  angle: 父亲送他造机器，他造出了哲学问题
  style: zinc
  status: published       # idea|approved|drafted|illustrated|reviewed|published|dropped
  sources:
    - 江怡《维特根斯坦传》第 2 章
    - 曼彻斯特大学档案
  facts:                  # 必须核完才能进 reviewed
    - 1906 入柏林夏洛滕堡
    - 1911 螺旋桨专利
  publish_id: yx5020261107906852835739542528
  folder: 2026.11.07_维特根斯坦05_工程师六年
  shelf_life: null        # 随笔填 48h，过期自动标 stale
```

**必须有的字段只有五个**：`id / title / type / angle / status`。其余按需。没有 `angle` 的选题不许进池——"想写点什么"不是选题。

### 4.2 评分决定先写哪条（随笔尤其需要）

四维各 0–5 分，总分排序，写脚本算，不靠感觉：

| 维度 | 判断标准 |
|---|---|
| 时效 | 48 小时内是热点窗口（5 分），一周内（3 分），无时限（1 分） |
| 独占 | 我有别人没有的材料/角度（5 分），只是转述（1 分） |
| 成本 | 半天能出（5 分），需查证多源（2 分） |
| 契合 | 与在手系列或账号主线一致（5 分），完全跑偏（0 分） |

规则：**总分 <8 不做**；同分按"能否在本周发"排序。

### 4.3 系列台账 `series.yaml`

系列与随笔最大的差别是**连续性**，所以系列多一层台账：

```yaml
id: wittgenstein
name: 哲人档案 · 维特根斯坦
style: zinc
status: done             # planning|writing|done|paused
plan: 00-系列_维特根斯坦/00-系列总纲.md
volumes:
  - {no: 1, title: 林荫巷16号, folder: 2026.11.07_维特根斯坦01_林荫巷16号, publish_id: yx...344}
  - {no: 2, title: 八个孩子, folder: 2026.11.07_维特根斯坦02_八个孩子, publish_id: yx...480}
bible:                   # 系列圣经：防止前后矛盾
  people: {汉斯: 长子，1902 失踪, 鲁迪: 1904 自杀, 保罗: 左手钢琴家}
  terms: {语言游戏: 后期核心概念，其二不出现}
  banned: [把"不可说"与家族沉默写成因果]
  canon: [凡不可说的必须保持沉默（通行中译）]
```

**bible 的用途**：写新一篇前先比对，人物生平、译名、口径不许和前面冲突。这是系列最容易翻车的地方，靠人记不住。

## 五、模块三：自动化创作（七步流水线，每步可单独重跑）

### 5.1 步骤与产物

| # | 步骤 | 谁做 | 产物 | 人审 |
|---|---|---|---|---|
| 1 | 选题 | 你/我提，写入 topics.yaml | topic 条目 | **必须** |
| 2 | 定位 | agent | `work/<id>/brief.md`（主问题、切口、3 个必写点、口径） | 可选 |
| 3 | 大纲 | agent | `work/<id>/outline.md`（章节 + 每章一句判断） | 可选 |
| 4 | 正文 | agent + 风格卡 + 模板 | `正文.html` | 可选 |
| 5 | 素材 | 脚本 | 封面 ×2、插图 ×N、上传后的 URL 清单 `assets.json` | 抽查 |
| 6 | 审查 | agent + 检查清单 | `review.md`（事实核查、口径、图位、标题字数、摘要字数） | **必须** |
| 7 | 发布归档 | 脚本 | publish_id 写回 manifest，git 提交 | **必须**（后台预览） |

### 5.2 三条硬规则

1. **幂等**：每步重跑覆盖自己的产物，不产生 `正文_v2_final.html` 这类垃圾。中间产物全在 `work/<id>/`，交付物才进文章文件夹。
2. **断点续跑**：任一环节失败，manifest 状态停在原地，修好后从该步继续，不从头来。
3. **单一写入口**：状态只能由脚本改，agent 不手改 status。否则台账必然失真。

### 5.3 状态机（非法跃迁直接拒绝）

```
idea → approved → outlined → drafted → illustrated → reviewed → published → archived
  ↘ dropped（任一阶段可弃）
```

约束：
- `reviewed` 的前置是 `facts` 全部核实 + 图片上传成功；
- `published` 必须有 `publish_id`；
- 跳过 `reviewed` 直接 `published` 会被脚本拒绝——这是防"忘了核事实就发"的最后一道闸。

## 六、目录规划（最小改动版）

保留"基础设施用 00- 前缀、文章用日期前缀"的现有习惯，只加两个目录：

```
E:/Writing/wx-mp/
├── 00-模板/                 # 已有：4 套正文模板 + 封面模板 + 生成器
├── 00-系统/                 # 新增
│   ├── 系统规划.md           # 本文
│   ├── styles/              # 4 张风格卡
│   ├── data/                # topics.yaml（选题池）
│   ├── schema/              # manifest / series 模板
│   └── tools/               # sys.py（状态/素材/推送）
├── 00-系列_维特根斯坦/       # 已有：总纲 + 生成器 → 加 series.yaml
├── 2026.11.07_维特根斯坦01_... # 文章仍是平铺日期目录，不搬家
└── scripts/                 # 已有：autocommit / watch
```

**为什么不把文章收进 `20-文章/`**：现在 25 个日期目录是交付单元，路径已经写进 manifest 和 git 历史。为了整齐再搬一次，收益是审美，成本是断链。等目录超过 60 个再考虑按年归档。

## 七、工具接口（agent 调脚本，脚本管状态）

```bash
python 00-系统/tools/sys.py status              # 全盘看板：状态/缺件/待审/过期选题
python 00-系统/tools/sys.py topic add --file t.yaml
python 00-系统/tools/sys.py topic rank          # 按四维评分排序
python 00-系统/tools/sys.py draft wtg-05        # 建 work/ 目录 + brief 骨架
python 00-系统/tools/sys.py assets wtg-05       # 截图 + 上传，写 assets.json
python 00-系统/tools/sys.py push wtg-05         # 上传图 + create + publish + 写回 publish_id
python 00-系统/tools/sys.py archive wtg-05      # 归档 + 更新 series.yaml + git 提交
```

分工原则：**写作归 agent，记账归脚本，发布归脚本，决策归你。** 不要让脚本试图"生成文章"——模板填空出来的东西一眼假。

## 八、实施路线（四阶段，每阶段有验收标准）

| 阶段 | 内容 | 验收标准 | 预估 |
|---|---|---|---|
| **P1 状态层** | manifest schema、topics.yaml、series.yaml、`sys.py status`、把现有 25 篇登记 | 一条命令列出每篇状态与缺件，无一条靠记忆 | 半天 |
| **P2 资产化** | 4 张风格卡、插图版式库（家族树/时间线/对照表/流程图/清单/引用卡）、封面生成器统一入口 | 新文章 0 手写 HTML 就能出封面 + 插图 | 1 天 |
| **P3 流水线** | draft/assets/push/archive 四段脚本 + 幂等 + 断点续跑 | 从选题到草稿箱 ≤5 次交互；中断后可续 | 1 天 |
| **P4 回流** | 选题评分脚本、系列 bible 冲突检测、阅读数据写回 | 新选题自动排序；新篇与 bible 冲突会被拦 | 持续 |

P1 不做完，后面全是空中楼阁。

## 九、反模式（写之前先认下来）

1. **模板填空化**：每篇强制保留 1 处"不套模板"的段落（一个场景、一句原话），否则写十篇一个味。
2. **选题池变垃圾场**：无 `angle` 不入池；7 天未动自动 `stale`；一个月清一次。
3. **台账失真**：只要允许手改 status，两周后就没法信。所有状态变更走脚本。
4. **过度自动化**：事实核查、口径、发布前预览三道人工卡点，任何阶段都不许自动跳过。名人传记、热点争议尤其如此。
5. **风格卡膨胀**：每张超过 300 字就退回 md 文档，卡的意义是"短到能整张塞进上下文"。
